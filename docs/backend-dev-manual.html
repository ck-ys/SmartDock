CHAPTER 03

开发流程

这一章是“照着做”的部分。每个流程都给顺序、图、代码骨架、常见错误和验收清单。

新增一个业务接口

  1. 定契约
    写清 URL、HTTP 动词、权限串、入参 BO、出参 VO。契约一旦被前端引用就是冻结的，改字段算破坏性变更。
  2. 判断要不要动表
    要动表就先做 3.2 的 DDL 双写；不动表直接写 domain。
  3. 写 domain
    BO 放入参和校验注解，VO 放出参；实体继承 BaseEntity，主键 ASSIGN_ID。
  4. 写 mapper
    自有单表直接用 BaseMapperPlus；跨表/复杂查询再写 XML 或注解 SQL。包名必须以 .mapper 结尾。
  5. 写 service
    编排用例、开事务、做归属校验。@Transactional 一律带 rollbackFor = Exception.class。
  6. 写 controller
    只做权限、参数、返回包装；不注入 mapper，不写业务分支。返回 R<T> 或 TableDataInfo<T>。
  7. 落权限串
    三段式写进 sys_menu.perms（baseline + migration），后端注解和前端 v-hasPermi 用同一串。
  8. 接前端
    在 api/dcs/<域>/<资源>.ts 加函数和 TS 类型，页面只调函数，不裸写 axios。
  9. 补单测
    纯函数/状态机优先，@Tag("local")；参照 AnalyticsSessionizerTest 的写法。
  10. 跑门禁 + 活体
    编译、单测、八条架构门禁、双视角活体；全绿才收口。

Controller 骨架

com/smartdock/<域>/controller/XxxController.java
@RestController
@RequestMapping("/dcs/xxx")
@RequiredArgsConstructor
public class XxxController extends BaseController {

    private final XxxService xxxService;

    @SaCheckPermission("dcs:xxx:list")
    @GetMapping("/page")
    public TableDataInfo<XxxVo> page(XxxBo bo, PageQuery pq) {
        return xxxService.page(bo, pq);
    }

    @RepeatSubmit
    @SaCheckPermission("dcs:xxx:add")
    @PostMapping
    public R<Void> add(@Validated @RequestBody XxxBo bo) {
        return toAjax(xxxService.add(bo));
    }
}

三条禁止

禁止自增主键、禁止物理删除、禁止外键与级联。唯一性必须落 DB 唯一索引，不许“先查再插”——并发下必出脏数据。

新表落地清单

新增一个业务模块

  1. 建目录与 pom
    在 backend/ruoyi-modules/ 下建模块，pom 的 parent 指 backend/pom.xml，依赖按需引 common 子模块。
  2. 根 pom 登记
    在根 <modules> 加一行；漏了这一步，Maven 根本不会构建它。
  3. 定包根
    com.smartdock.<域>，里面按 controller/service/domain/mapper 分层；不要新开层优先包。
  4. admin 装配
    ruoyi-admin/pom.xml 加依赖；启动类已扫 com.smartdock，不需要再改扫描。
  5. 跨模块收口
    要调别的模块，在消费方定义 gateway，实现放 admin 的 web/adapter；业务模块之间不直接依赖实现。
  6. DDL / 菜单 / 权限
    新表走双写，新页面写 sys_menu，权限串三段式。
  7. 门禁
    模块单测 + PackageHygieneTest + LayeringTest；新模块不能带新的 legacy 依赖。

定时任务与导出

新增定时任务

  • 任务类放 job/ 或所属域，方法无状态、可重入。
  • 大表分批：单轮 1 万行、封顶 100 轮，参照 ProfileRetentionJob。
  • 需要幂等：用唯一键或“先占坑再处理”，不要依赖执行一次。
  • 多实例要加分布式锁，避免两个节点同时跑。

新增导出

  • 用 FastExcel（ruoyi-common-excel），不手写 CSV。
  • 导出也要分页/分批，禁止一次性查全表。
  • 导出接口同样要 @SaCheckPermission，并做数据归属过滤。
  • 文件名带业务名和日期，避免浏览器重名覆盖。

CHAPTER 04

分层与包卫生

分层不是审美，是防止“改一处炸一片”的隔离带。这一章讲四层边界、gateway 判断和八条会红的门禁。

四层职责

层应该做不应该做
Controller登录/权限、参数校验、调用 service、包装返回写业务分支、注入 mapper、直接拼 SQL
Service用例编排、事务边界、归属校验、跨表协作返回 VO 之外的 UI 结构、依赖 controller
Domain实体、值对象、gateway 接口import service/controller/infrastructure/mapper
Infrastructuregateway 实现、外部客户端、legacy 适配反向被 domain import

gateway 建不建

建

  • 跨模块调用（消费方定义接口）
  • 流式/长连接（如 AGUI、SSE）
  • 外部服务（会换实现：模型、MCP、对象存储）

不建

  • 自有单表 CRUD：BaseMapper 已经是抽象
  • 只有一个实现的内部方法
  • 为了“看起来整洁”给每张表套一层

八条门禁

门禁跑在 ruoyi-admin 的单测里，只减不增。存量违规冻结在 arch-baseline.json，修一条删一行。

跑门禁
mvn -P local -DskipTests=false -pl ruoyi-admin -am test \
  -Dtest=PackageHygieneTest,LayeringTest,PackageMigrationGuardTest \
  -Dsurefire.groups=local,dev -DfailIfNoTests=false \
  -Dsurefire.failIfNoSpecifiedTests=false
#规则典型违规
1新代码只进 com.smartdock.<域>.<层>往 legacy 根新增文件
2禁止行内全限定名源码行里出现 org.dromara. / com.smartdock. / java.util.
3Controller 只做门卫方法超 40 行、注入 mapper、借别的模块 service
4出参不许 R<Map<String,Object>>图省事不定义 VO
5domain 不 import 上层domain 里 import service/mapper
6新根 service 对 legacy 只减不增新 service 直接 import legacy 类
7Mapper 包名以 .mapper 结尾放错包，MapperScan 静默不注册
8迁移守卫：类路径不出现旧根旧根改名后残留 class

CHAPTER 05

数据面

后端大部分“看起来像 bug”的问题，最后都落在租户、事务、索引和 JSONB 上。这一章把最容易静默出错的四件事单独拎出来。

多租户

业务表带 tenant_id，MyBatis-Plus 租户插件自动加条件。三条硬规则：

  1. 新表默认带 tenant_id；确实全局的表才进 tenant.excludes，并在评审里写明理由。
  2. 手写 SQL 被插件注入报“列不存在”：加 @InterceptorIgnore(tenantLine = "true")，并在 SQL 里自带 tenant_id 条件。

画像 profile

解决什么：任意业务事件 → 身份图谱 → 评分/分群/复核 → 快照趋势。事件是唯一入口，分数是算出来的，不手工改。

评分模型：一份 JSON，不是一堆 if

模型定义在 ProfileModelDefinition 解析：preset（GENERIC / RFM）+ dimensions[]，每个维度是「指标 + 分箱 + 权重」。分箱支持四种给法：edges（按边界切）、quantiles（按分位）、bands（枚举档）、n（等宽 N 段）；权重和必须大于 0，由 ProfileModelConfig 校验。计算入口 ProfileScoreEngine.recalcSubject：每个维度归一到 100 后加权合成总分；分箱打分在 ProfileBinResolver.resolve。

RFM 不是特判，是预设

通用模型没有独立的「等级」字段——等级只随 RFM 预设输出：八类分层是 ProfileRfmLevel 的纯函数，R/F/M 三档分界（rfmMid）定义在 ProfileModelDefinition。写文档别再写「指标→分箱→权重→等级」，等级不是通用链路的一环。

快照链：每次计算都能回放

每次计算都插一行快照，新行带 prev_snapshot_id 指向上一行，串成链。写入在 advisory 锁内做「读尾快照 → 插新行」两步，防止并发时链分叉成树。任何历史分数都能沿链回溯，评分模型改了也不影响旧快照的解释。

分群：扁平条件列表，不是条件树

能力入口要点
规则分群ProfileSegmentRulematch=ALL/ANY + 扁平 conditions[]（field/op/value），op 有 EQ/GT/IN/CONTAINS 等 11 种——是列表不是嵌套树，别按树去实现前端编辑器
预览ProfileSegmentService.preview保存前先看命中多少人
静态名单importMembers只有 STATIC 分群可导入；按 subjectId 精确匹配生成新 run

低分复核：打扰一次，别烦第二次

入队条件：reviewEnabled=1 且总分低于阈值（默认 60）；占位分（50）不入队。去重规则：上次已确认或已忽略、且分数没有继续下降，就不再入队——分数继续往下掉才会再次打扰。并发写入靠唯一索引兜底（捕获 DuplicateKeyException），不会双行。都在 ProfileReviewService。

AssistantAgentFactory 是唯一装配入口：create 在 L154 做公开组装，私有 create L158 负责实际构造，builder 在 L316 收尾。请求级差异（模型、工具集、记忆）都从这里注入，不要在业务里 new Agent。

装配项来源

系统提示词agent 定义 + 技能目录 + 日期 + 记忆

装饰器链见 8.6，顺序固定

装饰器洋葱

六层装饰器从内到外：思考档位 → 技能注入 → 日期注入 → 记忆注入 → PII → 计费。请求先过最外层，响应按相反顺序回来。

顺序不能随便调

PII 必须在计费之外、模型调用之内；如果把 PII 放到计费外层，脱敏后的 token 数与计费口径会对不上；把记忆放到 PII 外层，则会先读明文记忆再脱敏，泄露面变大；动态值（日期 / 记忆 / 技能）一律在末位追加——进前缀会击穿全租户的 prompt 缓存。

工具系统

工具分三层：平台内置 8 个、SPI 业务工具（3 个 Provider 共 14 个）、MCP 外部工具。三者最终汇成一个候选列表，再按权限闸裁剪。

层放哪加工具时改什么

SPI 业务业务模块实现 BizToolProviderProvider + 只读标记；不改助手模块
MCPdcs_mcp_server 配置后台登记服务器与工具开关，代码零改动

技能系统

技能是“可按需加载的提示词包”，不是工具。仓库分三层（内置 / 部署目录 / 数据库），目录不拼进系统提示词——由技能闸中间件在每次模型调用时按角色 + 权限矩阵 + 停用表重组 <skills> 段，正文命中后才注入。可见性变了下一轮立刻生效。

技能数会变，别背数字

当前内置 10 个（以仓库目录为准）。文档里的数字只能当锚点，实际以 ls 技能目录 + 装配日志为准。

会话与 run

ThreadSessionManager 以 (user, thread) 为键管理会话；一次 run 有明确的生命周期，任何一步失败都要留下可查状态。

状态含义前端表现
RUNNING跑动中；等人工确认（ask_user / interrupt）也是它，仅做收割豁免工作态 + 计时；HITL 卡
COMPLETED正常终答消息落库
FAILED失败，六类原因码落 dcs_assistant_run_issue错误卡 + 重试入口
INTERRUPTED模型中断 / 用户停止 / 客户端断连确认卡或停止态

HITL 与卡片

人工确认只有两个动作：查待确认、带决定重跑。没有“单独 resume 接口”——恢复靠下一次 /agui/run 附带全部 interrupt id。

恢复必须带全量 id

一次 run 可能产生多个 interrupt。只回传最后一个会导致其余确认丢失，run 卡在等待态。前端要按 GET /pending 的列表整批回传。

事件协议

28 个 AGUI 标准事件 + 11 个平台自定义帧。前端只认识这些名字，改名字等于改契约。

类别典型事件/帧用途
生命周期RunStarted / RunFinished / RunError开跑、收尾、失败
文本流TextMessageStart/Content/End逐字输出
工具ToolCallStart/Args/End、ToolCallResult工具卡片
状态StateSnapshot / StateDelta会话状态同步
自定义计划、待办、技能、计费、压缩、心跳等 11 帧专用卡片
加帧要三处同步

后端发帧 → 前端 onCustom 分支 → 卡片组件。只加后端等于“发了但没人渲染”，排查时先看前端 switch 有没有这个 name。

计费链

Agent 侧计费挂装饰器最外层，一次模型调用在返回后立刻结算；后台任务走另一条独立计费。两条链共用钱包，但幂等键不同。

已知边界，别当 bug 重报

幂等键只覆盖同一订阅内的重复帧。agent 重建或跨订阅重放，理论上仍可能重复计费。对账要按 run + 订阅组合看，发现差异先查这条，再定性。

提示词装配：8 段 md 拼出系统提示词

系统提示词不是一整个字符串，而是 8 段 markdown 按固定列表序拼装（PromptAssets）：role → discipline → discipline-urge → layout → cheatsheet → routes → chart → memory。加载三级兜底：config/prompts（部署期覆写）→ classpath prompts/ → 内嵌常量，和技能仓库同一套思路。

段什么时候拼
memory只有租户开记忆（memoryOn）才拼静态纪律段；动态记忆走装饰器（见 8.14）
discipline-urge催办纪律段，urgeVisible 才拼
cheatsheet / discipline装配时按本会话真注册的工具面裁剪（filterCheatsheet / filterDiscipline）——工具没开就不提它
日期不在前缀！每轮由装饰器在末位追加 system「今天是…」（见 8.6 顺序的原因）
计划没有独立段——只在纪律第 9 条要求模型调 submit_plan
技能目录不进系统提示词

旧版把技能目录拼进系统串的做法已退役。现在技能段由 AssistantSkillGateMiddleware（官方 DynamicSkillMiddleware 的子类）在每次模型调用时按角色 + skill: 权限闸 + 停用表重组 <skills>——可见性变了下一轮立刻生效，不用重建 agent。

记忆：一个写工具 + 一张用户私有表

模型侧只有 一个记忆工具 save_memory（写）；读、编辑、清空、删单条全走 REST（AssistantMemoryController），不占工具面。落表 dcs_assistant_memory，行是用户级私有（tenant_id + user_id 双谓词）——没有租户共享记忆这种东西。

开关管什么
租户 memoryEnabled整条记忆链装不装配：关了工具不注册、注入也不发生
个人 memory_pref用户自己的偏好开关

注入是动态的：AssistantMemoryService.digest 按最后一条用户提问做相关性打分取 TopK（30 秒缓存）；MemoryInjectModelDecorator 每次模型调用在末位追加 system「用户长期记忆：…」，无命中不注入；同时上报本轮注入条数与字数，供 memory_turn 帧显示。

排查「记忆没生效」

顺序：租户开关 → 个人开关 → digest 有没有命中（看缓存与相关性）→ 注入条数（memory_turn 帧）。四步都过才是真没写入。

上下文预算与压缩：两级减负

触发线公式（AssistantCompactionPolicy）：max(4000, 窗口 − min(最大输出, 21000) − 13000)——是绝对 token 数，不是百分比。到线后先微压缩，不够再主压缩。

参数值含义
keepMessages2最后 1 轮原文保留
triggerMessages0不按条数触发，只按 token
flushBeforeCompactfalse压缩前不先落盘
摘要输出封顶2 万 token摘要模型 tools 恒为 null（不许它调工具）

摘要模板九段：诉求 / 决定 / 编号 / 问题 / 偏好 / 待办 / 话题 / 下一步 / 红线，占位 {messages}。压缩后的上下文写回 AgentState（agentscope schema），同时在消息表落一条 role=system 的分隔条、dcs_assistant_compaction 落审计行（前后 token / 条数 / 摘要 / prev_id 链）。

双熔断，别当 bug

连续 3 次摘要失败、或压缩后 3 步内快速回填（说明压太狠），压缩自动停用。看到「上下文一直涨不压」先查是不是熔断了，而不是去改阈值。

run 状态机与多实例

run 的 status 是 String，只有四个取值：RUNNING / COMPLETED / FAILED / INTERRUPTED。没有 QUEUED、WAITING、DONE——等人工确认（ask_user / interrupt）期间 run 仍是 RUNNING，只做收割豁免。

机制口径
开跑insertIgnoreRun 写入 RUNNING，同刻绑定 tenant / user / thread / owner_instance
收尾终态都是条件 UPDATE（仅 status='RUNNING' 可迁移）；迟到的第二个终态直接丢弃，不会覆盖
实例身份配置 dcs.assistant.instance.id，缺省 hostname:pid:短码；租约 45 秒、心跳 15 秒
收割三档本机 60 秒无事件 → INTERRUPTED(client-disconnect)；纯心跳 10 分钟 → no-terminal-event；RetentionJob 每 15 分钟兜底迁移悬挂 run
跨实例owner 非本机且 Redis 租约未过期则不抢收；无 owner 的旧数据 30 分钟后才收

续看（attach）与回放汇

刷新页面后续看：先查 DB 最新 RUNNING，再 attach 本进程的汇（RunStreamHub）。汇不在本实例或已被逐出 → 返回失败，前端回退刷历史——跨实例不靠汇，靠粘性：LB 按 X-Thread-Id 哈希路由（AssistantStickyHeaderFilter 校验），没有粘性头多实例一启动就报错。

回放汇的五个窗口

单 run 保留 4096 帧；进程内最多 256 个 run；终局后留 300 秒；零观众 60 秒弃链；挂死 10 分钟弃链。溢出只重放最后 4096 帧，并在首帧补 dcs-resume-truncated——它是续看被截断的标记，和上下文压缩无关，别混。

只写 baseline，老环境升不上来；只写 migration，新环境建不出来。两处都写，才算交付。

4. 启动

启动参数（时区铁律）
java -Duser.timezone=GMT+8 -jar ruoyi-admin.jar
  • 后端固定 8090，单实例；多实例部署要另配租约与锁。
  • 启动日志里确认：密钥校验通过、迁移执行完毕、端口监听成功。
  • 前端固定 5188 直起；生产按实际网关配置，不要改端口跳号。

5. 冒烟

检查怎么验通过标准
登录admin 登录拿到 token，菜单完整
普通用户user001 登录菜单按权限裁剪，无 403 报错
核心列表画像/分析/任务各开一页有数据、分页正常
写操作建一条测试数据再删落库、审计字段正确
智能体发一句“你好”有流式帧、有终答、有计费记录
HITL触发一次确认卡片出现，确认后继续

6. 回滚与观察

回滚

  • 代码：回到上一个稳定 tag/commit，重新打包。
  • 库：优先向前修（migration 加一版），不轻易回滚数据。
  • 密钥：换回旧钥匙前确认旧密文仍在，否则解不开。

观察 30 分钟

  • 错误率、慢请求、连接池占用。
  • 智能体失败率与平均首帧时间。
  • 计费流水是否连续、有无重复。
  • 定时任务是否按点触发。
