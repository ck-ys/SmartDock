A · 标成熟度加深链★ 推荐
做什么
每条写成三段：一句话能力 + 成熟度标记 + 文档深链；成熟度只用三档，并给出判定标准——稳定可当地基（有单测覆盖、接口不再大改）/ 演进中（能用，但口径或界面还会动）/ 仅演示（只为把链路跑通）。同时补进分析中心三条与 MCP。
为什么
读参考实现的人最怕的不是功能少，是改进去才发现踩空。把「哪块能盖楼」提前标在地图上，等于替团队把话说在前面。
代价
成熟度是团队自己的判断，标错会误导，每次演进还要回来改；把「仅演示」摆到首页，可能劝退一部分只想要成品的读者。
B · 只加深链
做什么
同样补分析中心三条和 MCP，每条末尾加一个文档链接，但不写成熟度。
为什么
解决「看得到能力、点不进细节」这个真问题，改动十几行，不引入需要长期维护的判断。
代价
读者仍然不知道哪块能当地基、哪块会变，而这层信息恰恰是二次开发者最先要问的。
推荐 A：这个项目的卖点就是「敢给你看内部口径」，成熟度标记和深链是同一件事的两面——告诉你能拿哪块，以及凭什么。
Q2

跨天重播演示数据，清理这一步交给读者手动敲数据库、交给造数脚本自动做，还是干脆重建整个演示库？

造数脚本的事件编号带 demo- 前缀，同一天重复执行幂等；跨天会叠加。README:160 和 profile-engine.md:179 都只说「请先清掉旧的 demo- 前缀数据」，不给命令。 脚本只走 HTTP（登录 + 导入接口），参数只有 base/username/password/days/visitors。重建接口是同步的，所以「删完顺手重建」技术上可行。
清理不是删一张表：事件账本、主体登记、身份链接、访客首见都在库里，会话与日汇总要靠重建重算。
A · 文档给命令★ 推荐
做什么
README 写一段「先查后删」的 psql：按 demo- 前缀 + 租户条件，删事件账本、主体登记、身份链接、访客首见；删完照现有流程点一次「重建汇总」，并注明重建默认只覆盖最近 30 天。
为什么
零新代码，读者照抄即可；前缀加租户条件把误删范围锁死，先查后删也给了反悔的机会。
代价
要求读者连数据库、带口令；SQL 得覆盖四张表，写漏一张就留脏数据，文档也跟着变长；重建那一下还得人点。
B · 脚本一键重置
做什么
造数脚本加 --reset：直连数据库删掉 demo- 数据，删完自己调一次重建。
为什么
读者只记一条命令，不碰 SQL，也不会漏表。
代价
脚本从「只走 HTTP」变成还要数据库地址和口令；失败模式变多，表结构一变删除条件就得跟着改。
C · 重建库
做什么
文档明写「演示数据不是资产，跨天请重建一个空库再重新造数」。
为什么
零代码、零误删风险，语义最干净，也不给脚本开直连数据库的后门。
代价
读者要把建库、导入、重启再走一遍；库里一旦有真实数据这条路直接不可用；而且基线脚本只适用于空库，已有库要走 migration。
推荐 A：演示库本来就是一次性资产，为它写脚本删数据、或让脚本拿数据库口令，都是为省一步操作引入长期风险。

为什么

代价

代价

推荐 A：已有素材、几行改动，就能把「助手是真在跑」摆到首屏；横版视频更值得做，但它是一次持续维护承诺，等界面稳定后再上。

Q5

首页的测试用例数，是分组跑一轮换成真数、上自动流水线持续公布，还是干脆删掉数字？

README:339 写「后端 447 用例 + 前端 200 用例」。我实测：后端带测试标记的方法 890 处、分布在 169 个文件；而且标签是分组的（local / dev / p0probe），默认那条命令只跑 dev 组。 工作区里还有 136 份 surefire 报告，其中一份 RedteamCore8Test 有 8 个「应用上下文加载失败」。
所以「447」既不是静态全量 890，也不是默认 dev 组那一档——口径没人说得清；仓库也没有持续集成。
A · 分组跑一轮★ 推荐
做什么
按三个标签组分别跑一次（local 组也要本机 PostgreSQL，dev / p0probe 要数据库和缓存），再加一次前端 npm test；把四组数字、运行日期、默认命令只覆盖哪一组写进首页；顺手把已知 8 个上下文加载失败查清。
为什么
不用建基础设施，一次就能把数字变成可复现的真数；口径写清楚之后，读者跑同一条命令能对上。
代价
三组要分别跑，耗时以小时计；如果那 8 个错误是真的，这一步会先变成修测试，范围超出改文档。
B · 上自动流水线
做什么
配一条每次提交自动跑测试的流水线（三组都跑，带数据库和缓存服务），首页只写「以最近一次流水线结果为准」并挂结果入口。
为什么
数字从此不会再漂，测试坏了当场能看见，也补上「没有流水线」这个硬伤。
代价
要配运行环境、密钥、服务依赖和结果展示，是长期维护成本；而且现在那份 8 个错误会先把流水线变红，得先处理干净。
C · 删掉数字
做什么
只留覆盖范围（权限矩阵、状态机、个人信息脱敏、工具结果打标、写操作确认、协议与计费）和分组运行命令，不写数量。
为什么
零风险、不会说错，覆盖范围本身也有信息量。
代价
读者失去唯一能估量工程规模的证据；参考实现最想秀的「测得厚」反而看不见，以后测试有没有在跑也没人知道。
推荐 A：数字不可信的原因是口径没写、也没人跑；先分组跑一次把真数和口径落地，成本一次性。流水线更彻底，但得先有能稳定跑绿的测试。

A · 对齐后打标签★ 推荐
做什么
先核对管理台更新日志里最新已发布条目，把图注版本号对齐它；标签打在截图所在提交 a242a89；发行说明从该条目复制出来贴到发行页。
为什么
版本号、更新日志、可引用的发布点第一次对上，读者提问题时能说「我在 vX 上复现」。
代价
标签不在最新主干（落后两个提交），严格说发布点不是 HEAD；下一次发版要记得继续打。
B · 只锚提交编号
做什么
撤掉版本号，图注只写「a242a89 · 日期」，不打标签、不写发行说明。
为什么
零承诺、零维护，立刻不再说一句查不到的话，也够定位到具体哪一版。
代价
读者和问题里没有「版本」这个说法可用，只能贴一串编号；关注仓库的人也收不到发布通知。
C · 暂不发版
做什么
这轮不动，等下一个有完整更新日志的版本再一起打标签、改图注。
为什么
避免为一个已经过去的历史提交补一个没人消费的发版节点，省掉一次仪式性工作。
代价
在此之前这行字仍然和仓库、和更新日志都对不上；而「下一个版本」没有定义，很容易一拖再拖。
推荐 A：版本号对不上更新日志、标签不存在、截图又不是最新提交——这三个问题里有两个只要几分钟就能消掉。

3热门开源怎么做的（29 条里摘 12 条）

调研员实际拉取了 README / 文档站原文，每条都带链接。摘的是「我们明天就能照做」的那些。

RAGFlow学
快速开始不写「打开浏览器看看」，而是给一条可执行的就绪判据命令（健康检查 curl）。
→ 对应缺口 1：我们缺的就是这条判据。
Metabase改造后学
首屏顺序固定为「一句话定位 → 产品截图 → 徽章」；Key Features 每条都是「能力 + 一句限定 + 深链」。
→ 对应 Q1：能力清单加限定与深链，而不是堆形容词。
Dify学
Quick start 只保留一条能一次走通的最快路径，把自定义配置和进阶用法全部下沉到文档。
→ 对应 Q2：把「造数 → 重建 → 三条判据」写成一条能走通的路。
LobeChat学
把「部署跑起来」和「clone 下来改代码」拆成两个互不干扰的章节，各自有独立前置条件和步骤。
→ 我们的 README 已经分了方式一/方式二，可以再明确「只想跑」和「要改」。
Apache Superset学
用「Screenshots & Gifs」独立一节：先整段视频，再逐屏截图，每张图配一个能力名。
→ 对应 Q3：动图不是塞进首屏，而是给它一个「证明什么」的说明。
AgentScope 2.0改造后学
用 4 行表格装 4 张 GIF，每张下面是加粗行为名 + 一句「这一步实际发生了什么」。
→ 直接可套到我们的助手动图：三条「证明了什么」就是这句话。
PostHog学
README 里放一个折叠段，专门写给「被人类派来读仓库的 AI 代理」：MCP 端点、安装命令、llms.txt 索引。
→ 我们有 MCP 却没写，这条几乎是为我们准备的。
Plausible学
单开一节正面回答「为什么这东西不是免费的 / 为什么不能像 XX 那样用」，把商业模式和取舍摊开写。
→ 我们已有「不适合谁」，可以再补一句「和 SaaS 产品的边界」。
RuoYi-Vue-Plus学
第二屏放一张「本框架 vs RuoYi」的 46 行能力对照表，每行一个技术维度、左右两列写具体做法。
→ 我们上游就是它，一张「上游 vs 本仓库」表能一次讲清增量在哪。
芋道源码 yudao学
功能清单前先给分层图，再把模块分成三档：通用必选 / 通用可选 / 业务按需。
→ 和 Q1 的成熟度三档是同一个思路，可以直接借它的说法。
JeecgBoot学
第二个引擎不塞进主 README：主 README 只留一段简介 + 视频封面 + 一行「详细专题介绍请点这里」。
→ 我们的分析中心也可以走「主 README 三条 + 专题文档」的路子。
FastGPT改造后学
核心功能用 checkbox 列表写，已实现的打勾、没实现的留空，并按能力域编号分组。
→ 比「全打勾」诚实；但我们的未实现项不该上首页，需改造。
